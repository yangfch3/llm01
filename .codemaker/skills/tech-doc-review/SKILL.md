# 技术文档评审

按 Checklist 逐项检查 + 自由评审，输出结构化报告到 `.ai_review/`。

## 评审流程

1. 接收文档路径或内容
2. 通读全文，建立整体理解
3. Checklist 逐项检查（6 维度 19 项），每项 ✅ / ⚠️ / ❌ + 简要说明
4. 跳出 Checklist 做自由评审
5. 给出具体可操作的改进建议
6. 写入报告（不在会话中展示完整报告，只给一句话摘要）

## Checklist

### 1. 结构完整性

- 1.1 背景/目标/动机
- 1.2 功能范围（Scope）
- 1.3 边界（Out of Scope）
- 1.4 术语/缩写定义 — 仅项目特有非通用术语需定义

### 2. 功能描述清晰度

- 2.1 无歧义性
- 2.2 输入/输出/行为
- 2.3 异常/边界场景
- 2.4 优先级区分（Must vs Nice-to-have）

### 3. 技术可行性

- 3.1 架构兼容性
- 3.2 风险与依赖
- 3.3 性能指标（量化）
- 3.4 安全性/权限/隐私
- 3.5 框架影响 — 是否对现有框架造成破坏性变更或连带风险
- 3.6 可扩展性

### 4. 一致性与关联性

- 4.1 内部自洽
- 4.2 与已有文档/系统一致
- 4.3 关联模块/接口引用清晰

### 5. 可测试性

- 5.1 可转化为测试用例
- 5.2 验收标准明确

### 6. 可维护性与可读性

- 6.1 组织结构/章节层次
- 6.2 图表辅助（如适用）

**评分**：✅ 通过 / ⚠️ 待改进 / ❌ 缺失或不合格

## 评审原则

- **上下文优先** — 先判断文档定位（MVP / 正式需求 / 原型验证）和目标读者，据此调整严格程度。不对 MVP 文档提生产级要求
- **只输出问题和建议** — 不写恭维性语句
- **不吹毛求疵** — 在该文档定位下不适用的检查项直接 ✅ 标注"该场景无需关注"
- **具体可操作** — 每条建议具体到能直接执行
- **分清轻重** — 🔴 关键 / 🟡 建议 / 🟢 可选
- **保持客观** — 无法判断时标「无法判断」，不猜测

## 输出规范

1. **路径**：`.ai_review/<文档名>-review-<YYYYMMDD-HHmmss>.md`
2. **模板**：读取 `references/report-template.md` 按模板输出
3. **格式**：UTF-8、LF、末尾空行、无 BOM
